    max-bot-template

    Готовая основа для ботов на платформе MAX с настроенным CI/CD под GitHub Actions и Gitea Actions. TypeScript-аналог шаблона template-max-bot-github-gitea — та же архитектура и те же решения, перенесённые на Node.js.

    Разработка

    Работа с платформой построена на официальном клиенте @maxhub/max-bot-api (Telegraf-подобный API: bot.command()/bot.hears()/bot.action(), ctx.reply(), Keyboard.inlineKeyboard()). Он поддерживает только long polling — webhook в нём не реализован, поэтому фоновая очередь приёма апдейтов (src/webhook.ts) и подписка/отписка от webhook (src/maxWebhookSubscription.ts, единственный best-effort фрагмент — путь /subscriptions нигде не покрыт официальным клиентом) остались собственными. Троттлинг, ретраи на 429 и кастомный CA патчат globalThis.fetch (src/runtime.ts) — клиент не даёт для этого своих хуков.

    Шаблон закрывает то, что в каждом новом боте приходится писать заново: ограничение частоты запросов к API, корректное завершение процесса, разбор конфигурации с проверками, режимы polling/webhook, сборка образа и деплой с откатом. Из коробки это бот-визитка: дерево разделов меню хранится в Postgres и правится прямо в MAX командой /admin — без правки кода и передеплоя. Работа с админкой описана в docs/admin-guide.md.

    Быстрый старт#

    cp .env.example .env          # задать MAX_BOT_TOKEN и ADMIN_IDS
make install                  # pnpm install
make up-local-db              # Postgres в Docker на 127.0.0.1:5433
make run                      # миграции + запуск в режиме polling

    Или всё в Docker одной командой: make up-local (бот и Postgres, миграции применяются при старте контейнера).

    Токен бота выдаёт @masterbot в мессенджере MAX. Свой user_id бот покажет по команде /id. Дальше — /admin в личке с ботом.

    По умолчанию PROD=false — бот отвечает только тем, чьи id перечислены в ADMIN_IDS. Это защита от преждевременного выхода к пользователям: пока бот не настроен, посторонний увидит заглушку.

    Создание нового проекта#

    make init

    Скрипт спросит имя (kebab-case) и описание, затем:

    • подставит имя в package.json, оба compose-файла и пайплайн Gitea;
    • заменит README заготовкой, а этот файл сохранит как docs/TEMPLATE.md;
    • удалит сам себя;
    • начнёт историю git заново одним коммитом (--keep-git отключает).

    Неинтерактивно:

    pnpm run init-project -- --name support-max-bot --description "Бот техподдержки"

    После инициализации разделы меню и приветствие правятся в админке (/admin), стартовое наполнение — в миграции migrations/1763294400000_initial.js.

    Конфигурация#

    Все параметры читаются из окружения (или .env в корне). Полный список с пояснениями — в .env.example; ниже основное.

    Переменная По умолчанию Назначение
    MAX_BOT_TOKEN — Обязательна. Токен бота
    BOT_MODE polling polling или webhook
    PROD false false — только владельцы, true — все
    ADMIN_IDS пусто Владельцы бота, user_id через запятую
    LOG_LEVEL info debug/info/warning/error
    PORT 8081 Порт webhook-сервера
    WEBHOOK_HOST — Обязательна при BOT_MODE=webhook
    WEBHOOK_SECRET — Обязательна при BOT_MODE=webhook
    MAX_API_RPS 25 Общий лимит запросов к API
    MAX_API_MESSAGE_RPS 2 Лимит отправки сообщений
    MAX_CA_BUNDLE — Путь к дополнительному корневому сертификату
    DATABASE_URL — Обязательна. DSN Postgres (postgresql://…)
    POSTGRES_USER / POSTGRES_PASSWORD / POSTGRES_DB bot Креды Postgres для compose; на проде пароль обязателен
    STATS_ENABLED true Записывать открытия разделов
    STATS_SALT пусто Секрет хеша посетителя; пусто — MAX_BOT_TOKEN
    DISPLAY_UTC_OFFSET 3 Часовой пояс времени в админке, часов от UTC
    METRICS_ENABLED false HTTP-сервер метрик
    BUILD_TAG пусто Заполняется при деплое, показывается в /v

    Конфигурация проверяется при старте (zod-схема + ручные проверки), а не при первом обращении: бот не запустится с webhook без секрета или без DATABASE_URL. Ошибка на старте дешевле, чем открытый эндпоинт или падение под нагрузкой.

    Режимы работы: polling и webhook#

    Polling (BOT_MODE=polling) — бот сам опрашивает платформу через GET /updates. Ничего не слушает, публичный адрес не нужен. Режим для разработки.

    Webhook (BOT_MODE=webhook) — платформа шлёт апдейты на ваш адрес. Бот поднимает встроенный HTTP-сервер (node:http, без фреймворка), регистрирует подписку при старте и отдаёт /healthz.

    Что нужно для webhook:

    BOT_MODE=webhook
WEBHOOK_HOST=https://bot.example.ru      # публичный https без пути
WEBHOOK_SECRET=$(openssl rand -hex 32)   # обязателен
PORT=8081

    Секрет обязателен намеренно: без него маршрут принимал бы любой POST от кого угодно. Шаблон отказывается стартовать в такой конфигурации.

    Обработка апдейтов вебхука#

    Маршрут вебхука (src/webhook.ts) отвечает MAX сразу, а обработка уходит в фоновую задачу — HTTP-соединение не удерживается на всё время работы хендлера. Очередь фоновой обработки ограничена WEBHOOK_MAX_PENDING_UPDATES: сверх лимита новые апдейты получают 503 (MAX повторит доставку), а не копятся в открытых сокетах. Текущий размер очереди виден в /healthz полем pending_updates. При остановке бот ждёт WEBHOOK_DRAIN_TIMEOUT секунд, чтобы дообработать уже принятое — с оговоркой: в отличие от asyncio.Task в Python, Promise в JS нельзя отменить, поэтому по истечении таймаута метод просто перестаёт ждать (см. «Отличия от Python-версии»).

    Про дубли апдейтов#

    Платформа повторяет апдейт, если не получила подтверждение вовремя. Дедупликации по update_id в шаблоне нет — если ваши обработчики выполняют неидемпотентные действия (списание, запись в БД, отправка уведомления), добавьте её сами.

    Уровни доступа#

    1. Maintenance-гейт (middlewares/maintenance.ts) — при PROD=false пропускает только владельцев из ADMIN_IDS. Работает как outer middleware, то есть до фильтров: перехватывает сообщения, нажатия кнопок и bot_started одним кодом. В группах при блокировке молчит — отвечать на каждое упоминание значит спамить чат.

    2. Ограничение частоты (middlewares/throttling.ts) — не чаще одного события на пользователя в 0.5 с. Состояние хранится в памяти процесса, поэтому при нескольких репликах лимит становится приблизительным; для честного распределённого лимита нужен Redis.

    3. Роли админки (handlers/admin.ts). Владелец — ADMIN_IDS из .env: всё, включая управление администраторами. Администратор — добавлен владельцем в «👥 Админы» (таблица staff): правка разделов, статистика, файл, журнал. Роль читается из БД на каждом событии — отозванный администратор теряет доступ сразу. Неадминам /admin, /v, /status не отвечают вовсе: сообщение «недостаточно прав» само по себе раскрывает наличие скрытых функций. Админка открывается только в личке.

    Как добавить функциональность#

    Новый раздел меню#

    Код не нужен: /admin → «➕ Добавить подраздел». Стартовые разделы для новых установок — в seed миграции migrations/1763294400000_initial.js (для уже развёрнутой БД — новой миграцией или файлом «📦 Файл → ⬆️ Загрузить»).

    Новая команда#

    // src/handlers/myFeature.ts
import type { Context } from "@maxhub/max-bot-api";
import type { Dispatcher } from "./index.js";

export function register(bot: Dispatcher): void {
  bot.command("mycommand", onMyCommand);
}

async function onMyCommand(ctx: Context): Promise<void> {
  await ctx.reply("Ответ");
}

    Затем добавить myFeature.register(bot) в registerHandlers() (handlers/index.ts) — до menu.register(bot), иначе catch-all на свободный текст перехватит команду раньше.

    Новый тип кнопки#

    Опишите payload классом в keyboards/callbacks.ts (по образцу SectionPayload/AdminPayload) и обработайте его своим bot.action(/^x:/, …) до menu.register(). Новое действие админки — значение в AdminAction, кнопка в keyboards/menus.ts, ветка в handlers/editor.ts (над разделом) или handlers/tools.ts (инструмент главного экрана). Формат payload задан в одном месте намеренно.

    База данных#

    БД обязательна: разделы меню, администраторы, статистика и журнал живут в Postgres.

    Таблица Что хранит
    sections дерево разделов: parent_id (корень — NULL, его текст — приветствие), title, text, position, url, image_token; удаление каскадное
    staff администраторы, добавленные владельцем
    section_views открытия разделов: HMAC-хеш посетителя вместо user_id; удаление раздела ставит NULL
    audit_log журнал правок админки — в той же транзакции, что и правка

    Миграции#

    make up-local-db                          # поднять Postgres в Docker
make migration m="добавил таблицу"        # создать ревизию (node-pg-migrate)
make migrate                              # применить к DATABASE_URL из .env

    Миграции — обычные JS-файлы (.node-pg-migraterc задаёт migration-file- language: js), DSN берётся из DATABASE_URL в .env — make migrate сам подгружает .env. make run применяет миграции перед стартом, контейнер — тоже (CMD в docker/Dockerfile). Начальная миграция написана чистым SQL через pgm.sql(): ту же схему тесты прогоняют на PGlite.

    Использование#

    import { withTransaction } from "./db/pool.js";
import { SectionRepository } from "./db/repositories/sections.js";

const root = await withTransaction((db) => new SectionRepository(db).root());

    Весь SQL держится в репозиториях. Обработчики к пулу напрямую не ходят: иначе запросы расползаются по слоям и их невозможно ни переиспользовать, ни протестировать отдельно.

    Метрики#

    # .env
METRICS_ENABLED=true
METRICS_ADDR=:9090

    Сервер поднимается на отдельном порту и наружу не публикуется — его забирает Prometheus изнутри сети. Счётчики описаны в src/metrics.ts. prom-client — optionalDependency, импортируется лениво.

    Docker#

    Образ многостадийный (docker/Dockerfile):

    • base — зависимости и код, pnpm build в TypeScript; отдельный слой на package.json/pnpm-lock.yaml, чтобы правка кода не тянула переустановку пакетов;
    • test — гоняет biome check и vitest внутри собранного образа; эту цель использует CI, проверяя ровно ту среду, что поедет на прод;
    • runtime — прод-образ: pnpm prune --prod убирает dev-зависимости (typescript, vitest, biome, tsx), запуск от непривилегированного пользователя (appuser, uid 10001).

    Compose#

    docker-compose.local.yml собирает образ из исходников — разработчику нужно видеть свои правки. Postgres поднимается вместе с ботом и слушает 127.0.0.1:${POSTGRES_PORT:-5433} — для make run и make migrate с хоста.

    docker-compose.prod.yml тянет готовый образ из Harbor по тегу, выставляет лимиты памяти и CPU и публикует бота через внешнюю сеть maxbots-network, а не пробросом порта на хост. Postgres наружу не публикуется, имя хоста базы уникальное (max-bot-template-db) — чтобы не совпасть с базой другого бота той же сети. POSTGRES_PASSWORD в прод-.env обязателен: длинный и без символов @ : / ? # — он подставляется в DSN как есть.

    В обоих файлах DATABASE_URL для бота собирается из POSTGRES_* в самом compose: внутри сети база доступна по имени сервиса, а не по 127.0.0.1 из .env.

    Оба файла принимают --env-file .env — это обязательно. Без флага Compose ищет .env рядом с самим compose-файлом, то есть в docker/, и подстановка ${PORT} в ports: молча берёт значение по умолчанию. Makefile подставляет флаг сам.

    Healthcheck в прод-конфигурации бьёт в /healthz (через node -e, без дополнительных зависимостей) и потому работает только при BOT_MODE=webhook. Для polling его нужно убрать, иначе исправный бот будет помечен unhealthy.

    CI/CD#

    GitHub Actions (.github/workflows/ci.yml)#

    Три задачи: lint → test → build. Сборка проверяет валидность обоих compose-файлов, собирает образ и публикует его в GHCR (на pull request — только собирает, без публикации). Теги: latest на дефолтной ветке, семантические на v*.*.*, sha-<short> всегда.

    Gitea Actions (.gitea/workflows/pipeline.yml)#

    Один файл на весь цикл: lint → test → build → release-image → deploy → rollback.

    Почему один файл, а не ci.yml + cd.yml. В Gitea Actions нет события workflow_run (gitea#24898), поэтому запустить деплой «после успешного CI» из отдельного файла нечем. Единственный рабочий способ выстроить зависимость — needs: внутри одного файла.

    Не добавляйте рядом второй workflow с теми же триггерами: Gitea запускает каждый файл в .gitea/workflows/ независимо, и вы получите двойные прогоны.

    Что происходит при пуше тега vX.Y.Z:

    1. build собирает образ и публикует его как sha-<short>;
    2. release-image находит этот образ и перетегивает в vX.Y.Z без пересборки (если не нашёл — собирает из исходников тега);
    3. deploy копирует compose на прод-хост, сохраняет предыдущий тег в .image_tag.previous, делает pull и up -d, затем проверяет, что контейнер запущен и не уходит в рестарт-петлю;
    4. rollback срабатывает автоматически при провале и возвращает предыдущий тег.

    Файл .env через пайплайн не ходит: боевые секреты лежат на прод-хосте постоянно.

    Требуемые Gitea Variables: HARBOR_REGISTRY, HARBOR_PROJECT, HARBOR_IMAGE, RUNNER_LABEL, PROD_HOST, PROD_USER, PROD_PATH, NPM_REGISTRY (опц.).

    Требуемые Gitea Secrets: HARBOR_USERNAME, HARBOR_PASSWORD, SSH_PRIVATE_KEY, NPM_REGISTRY_TOKEN (опц.).

    Про smoke-тест образа#

    Полный старт бота в CI не проверяется: с плейсхолдер-токеном первый же запрос к API вернёт ошибку авторизации, и гейт был бы красным при полностью исправной сборке. Вместо этого проверяется импорт собранного модуля конфигурации внутри готового образа — он тянет все зависимости и строит конфигурацию, то есть ловит именно ошибки сборки, без сети и без реального токена.

    Закрытый контур#

    Шаблон настроен на работу за периметром, но остаётся работоспособным снаружи.

    По умолчанию источники указывают на внутренние зеркала: harbor.volganet.ru (образы), nexus.volganet.ru (APT), Gitea Variable NPM_REGISTRY (npm-прокси, если он есть). Все они параметризованы.

    Сборка с доступом в интернет:

    BASE_IMAGE=node:24-bookworm-slim \
POSTGRES_IMAGE=postgres:18-alpine \
USE_NEXUS_APT=0 \
make up-local

    Workflow для GitHub уже собирает с публичными источниками — у его раннера доступа к контуру нет.

    Раннер Gitea. В отличие от Python-версии шаблона (которой приходится вендорить бинарь uv в build/uv/, потому что раннер не может скачать его с astral.sh), здесь ничего вендорить не нужно: corepack (менеджер пакетных менеджеров) входит в поставку Node.js, и pnpm активируется одной командой corepack enable. Раннеру достаточно иметь предустановленный Node 24.

    Сертификаты. Если цепочка API подписана УЦ, которого нет в системном хранилище (например, Минцифры РФ), есть два пути — положить .crt в certs/ (действует на весь контейнер) или указать MAX_CA_BUNDLE (действует только на соединения бота). Подробности в certs/README.md.

    Токены в реестре. NPM_REGISTRY может содержать креды внутреннего npm-прокси. В пайплайне он маскируется и передаётся через окружение шага.

    Документация#

    docs/*.md — источник правды, make docs собирает из них HTML в docs/html/ (открывается без сервера: docs/html/index.html). Главная страница — этот README. Стили и скрипт страниц — scripts/docs-assets/, разделы навигации — SECTIONS в scripts/build-docs.ts.

    Тесты#

    make test

    142 теста: конфигурация, payload'ы и клавиатуры, репозиторий дерева разделов, сценарии админки целиком (добавить раздел → задать текст → пользователь его видит → удалить), картинки и откат на экран без картинки, кнопки-ссылки, администраторы, статистика, экспорт/импорт, журнал, ограничитель частоты, throttling, очередь вебхука.

    Сценарные тесты прогоняют апдейты через настоящую цепочку хендлеров (registerHandlers() — тот же порядок, что в проде), вызовы MAX API пишет FakeApi из tests/helpers/bot.ts. Postgres — PGlite (Postgres в WASM, в процессе, без Docker и сети), схема — из той же миграции, что в проде (tests/helpers/db.ts).

    Тесты герметичны: в сеть не ходят, реальный токен не используют, локальный .env игнорируют (src/config.ts не грузит .env, когда переменная VITEST выставлена — vitest сам её ставит на время прогона).

    Помощник withEnv() из tests/helpers/env.ts задаёт переменные окружения так же, как это делает прод, — заодно проверяется и сам разбор конфигурации:

    it("разбирает список admin id", () => {
  const settings = withEnv({ ADMIN_IDS: " 123, 456 ,789 " });
  expect(settings.adminIdsSet).toEqual(new Set([123, 456, 789]));
});

    Отличия от Python-версии#

    Короткий список мест, где TypeScript-порт устроен иначе, чем оригинал, и почему.

    Официальный клиент вместо maxapi. Python-версия оборачивает библиотеку maxapi. Здесь используется официальный @maxhub/max-bot-api — тот же принцип (сторонний/официальный клиент под собственной инфраструктурой лимитов и очереди), но с настоящим, поддерживаемым SDK вместо стороннего.

    Webhook собран поверх официального клиента, а не входит в него. @maxhub/max-bot-api поддерживает только long polling. Для webhook шаблон конструирует Context из сырого JSON и прогоняет её через bot.middleware() — так вся маршрутизация (bot.command()/bot.action()/ bot.on(), зарегистрированные в handlers/) работает одинаково в обоих режимах. Подписка/отписка от webhook (maxWebhookSubscription.ts) написана вручную и промаркирована как best-effort: это единственный путь API, который официальный клиент не покрывает и не подтверждает.

    Лимиты и ретраи патчат globalThis.fetch, а не monkey-patch конкретного класса. Python-версия патчит BaseConnection.request библиотеки maxapi. Официальный клиент MAX для TS не даёт ни хуков, ни доступа к своему HTTP-слою, поэтому единственная точка перехвата — глобальный fetch, который он вызывает напрямую (runtime.ts::patchFetchForRateLimiting).

    Webhook-сервер — node:http, без фреймворка. Вместо FastAPI + uvicorn здесь используется встроенный HTTP-сервер Node: обработчиков всего два (POST-маршрут вебхука и /healthz), фреймворк не оправдан.

    drain() не отменяет задачи. asyncio.Task в Python можно отменить; Promise в JS — нет. По истечении WEBHOOK_DRAIN_TIMEOUT бот просто перестаёт ждать, фоновые обработчики доработают самостоятельно (см. комментарий в src/webhook.ts).

    Метрики — optionalDependencies, а не extras. В Python metrics ставится по требованию (uv sync --extra metrics). В Node аналог — optionalDependencies в package.json: prom-client ставится вместе с pnpm install, но импортируется лениво, поэтому его можно убрать из package.json, если метрики не нужны.

    DSN без суффикса драйвера. Python-версия требует postgresql+asyncpg:// и проверяет это при старте — синхронный драйвер иначе не заработал бы молча. pg в Node всегда асинхронный, поэтому DATABASE_URL — обычный postgresql:// (проверяется только схема DSN).

    SQL без ORM, тесты на PGlite. Вместо SQLAlchemy + Alembic — pg и node-pg-migrate, весь SQL в src/db/repositories/. Python-тесты гоняют переносимые запросы на SQLite; здесь — на PGlite, то есть на настоящем Postgres-диалекте (рекурсивные CTE, ON CONFLICT, каскады).

    Длина ввода — в символах Unicode. Лимиты MAX (64 на кнопку, 4000 на текст) считаются как len() в Python, а не как String.length, который посчитал бы эмодзи за два.

    Формат файла разделов общий. max-bot-sections, версия 1 — файл, выгруженный Python-ботом, загружается в TS-бот и наоборот.

    Разделы меню и тексты в шаблоне демонстрационные — правьте их в админке. Инфраструктура (конфигурация, лимиты, режимы, сборка, деплой) переносится как есть.
