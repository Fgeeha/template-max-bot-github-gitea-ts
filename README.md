# Шаблон чат-бота для мессенджера MAX (TypeScript)

Готовая основа для ботов на платформе [MAX](https://max.ru) с настроенным
CI/CD под **GitHub Actions** и **Gitea Actions**. TypeScript-аналог шаблона
[template-max-bot-github-gitea](../template-max-bot-github-gitea) — та же
архитектура и те же решения, перенесённые на Node.js.

Официального Node/TS SDK для MAX Bot API не существует, поэтому в шаблон
включён тонкий вендоренный клиент (`src/max/`), покрывающий ровно то, что
используют хендлеры: отправку и удаление сообщений, инлайн-клавиатуры,
подписку на webhook и long polling. Перед продом сверьте пути эндпоинтов с
актуальной документацией: https://dev.max.ru/.

Шаблон закрывает то, что в каждом новом боте приходится писать заново:
ограничение частоты запросов к API, корректное завершение процесса, разбор
конфигурации с проверками, режимы polling/webhook, сборка образа и деплой с
откатом.

## Быстрый старт

```bash
cp .env.example .env          # задать MAX_BOT_TOKEN и ADMIN_IDS
make install                  # pnpm install
make run                      # запуск в режиме polling
```

Токен бота выдаёт `@masterbot` в мессенджере MAX. Свой `user_id` можно узнать
у `@userinfobot`.

По умолчанию `PROD=false` — бот отвечает только тем, чьи id перечислены в
`ADMIN_IDS`. Это защита от преждевременного выхода к пользователям: пока бот
не настроен, посторонний увидит заглушку.

## Создание нового проекта

```bash
make init
```

Скрипт спросит имя (kebab-case) и описание, затем:

- подставит имя в `package.json`, оба compose-файла и пайплайн Gitea;
- заменит README заготовкой, а этот файл сохранит как `docs/TEMPLATE.md`;
- удалит сам себя;
- начнёт историю git заново одним коммитом (`--keep-git` отключает).

Неинтерактивно:

```bash
pnpm run init-project -- --name support-max-bot --description "Бот техподдержки"
```

После инициализации остаётся заменить разделы меню в
`src/keyboards/menus.ts` и текст приветствия в `src/handlers/start.ts`.

## Конфигурация

Все параметры читаются из окружения (или `.env` в корне). Полный список с
пояснениями — в [`.env.example`](.env.example); ниже основное.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `MAX_BOT_TOKEN` | — | **Обязательна.** Токен бота |
| `BOT_MODE` | `polling` | `polling` или `webhook` |
| `PROD` | `false` | `false` — только администраторы, `true` — все |
| `ADMIN_IDS` | пусто | user_id через запятую |
| `LOG_LEVEL` | `info` | debug/info/warning/error |
| `PORT` | `8081` | Порт webhook-сервера |
| `WEBHOOK_HOST` | — | Обязательна при `BOT_MODE=webhook` |
| `WEBHOOK_SECRET` | — | Обязательна при `BOT_MODE=webhook` |
| `MAX_API_RPS` | `25` | Общий лимит запросов к API |
| `MAX_API_MESSAGE_RPS` | `2` | Лимит отправки сообщений |
| `MAX_CA_BUNDLE` | — | Путь к дополнительному корневому сертификату |
| `DATABASE_URL` | — | DSN Postgres; без неё слой БД не поднимается |
| `METRICS_ENABLED` | `false` | HTTP-сервер метрик |
| `BUILD_TAG` | пусто | Заполняется при деплое, показывается в `/v` |

Конфигурация проверяется при старте (zod-схема + ручные проверки), а не при
первом обращении: бот не запустится с webhook без секрета. Ошибка на старте
дешевле, чем открытый эндпоинт или падение под нагрузкой.

## Режимы работы: polling и webhook

**Polling** (`BOT_MODE=polling`) — бот сам опрашивает платформу через
`GET /updates`. Ничего не слушает, публичный адрес не нужен. Режим для
разработки.

**Webhook** (`BOT_MODE=webhook`) — платформа шлёт апдейты на ваш адрес. Бот
поднимает встроенный HTTP-сервер (`node:http`, без фреймворка), регистрирует
подписку при старте и отдаёт `/healthz`.

Что нужно для webhook:

```bash
BOT_MODE=webhook
WEBHOOK_HOST=https://bot.example.ru      # публичный https без пути
WEBHOOK_SECRET=$(openssl rand -hex 32)   # обязателен
PORT=8081
```

Секрет обязателен намеренно: без него маршрут принимал бы любой POST от кого
угодно. Шаблон отказывается стартовать в такой конфигурации.

### Обработка апдейтов вебхука

Маршрут вебхука (`src/webhook.ts`) отвечает MAX сразу, а обработка уходит в
фоновую задачу — HTTP-соединение не удерживается на всё время работы
хендлера. Очередь фоновой обработки ограничена `WEBHOOK_MAX_PENDING_UPDATES`:
сверх лимита новые апдейты получают 503 (MAX повторит доставку), а не копятся
в открытых сокетах. Текущий размер очереди виден в `/healthz` полем
`pending_updates`. При остановке бот ждёт `WEBHOOK_DRAIN_TIMEOUT` секунд, чтобы
дообработать уже принятое — с оговоркой: в отличие от `asyncio.Task` в Python,
`Promise` в JS нельзя отменить, поэтому по истечении таймаута метод просто
перестаёт ждать (см. [«Отличия от Python-версии»](#отличия-от-python-версии)).

### Про дубли апдейтов

Платформа повторяет апдейт, если не получила подтверждение вовремя.
Дедупликации по `update_id` в шаблоне **нет** — если ваши обработчики
выполняют неидемпотентные действия (списание, запись в БД, отправка
уведомления), добавьте её сами.

## Уровни доступа

1. **Maintenance-гейт** (`middlewares/maintenance.ts`) — при `PROD=false`
   пропускает только `ADMIN_IDS`. Работает как outer middleware, то есть до
   фильтров: перехватывает сообщения, нажатия кнопок и `bot_started` одним
   кодом. В группах при блокировке молчит — отвечать на каждое упоминание
   значит спамить чат.

2. **Ограничение частоты** (`middlewares/throttling.ts`) — не чаще одного
   события на пользователя в 0.5 с. Состояние хранится в памяти процесса,
   поэтому при нескольких репликах лимит становится приблизительным; для
   честного распределённого лимита нужен Redis.

3. **Обёртка `adminOnly`** (`handlers/admin.ts`) — служебные команды.
   Неадминам такие команды не отвечают вовсе: сообщение «недостаточно прав»
   само по себе раскрывает наличие скрытых функций.

## Как добавить функциональность

### Новый раздел меню

Достаточно дописать запись в `SECTIONS` (`src/keyboards/menus.ts`) — кнопка и
обработчик подхватят её сами:

```typescript
{
  id: "contacts",
  title: "📞 Контакты",
  text: "Телефон: +7 000 000-00-00",
},
```

Есть тест, который проверяет, что каждая кнопка ведёт в существующий раздел.

### Новая команда

```typescript
// src/handlers/myFeature.ts
import { command } from "../max/filters.js";
import type { Dispatcher } from "../max/dispatcher.js";
import type { MessageCreated } from "../max/types.js";

export function register(dp: Dispatcher): void {
  dp.onMessageCreated(onMyCommand, command("mycommand"));
}

async function onMyCommand(event: MessageCreated): Promise<void> {
  await event.message.answer({ text: "Ответ" });
}
```

Затем добавить `myFeature.register(dp)` в `handlers/index.ts` — **до**
`menu.register(dp)`, иначе catch-all на свободный текст перехватит команду
раньше.

### Новый тип кнопки

Опишите payload классом в `keyboards/callbacks.ts` (по образцу `MenuPayload`)
и обработайте его в `handlers/menu.ts::onCallback`. Формат payload задан в
одном месте намеренно.

## База данных

Слой БД опционален. Бот без состояния работает без него — каталог `src/db/`
и `migrations/` можно удалить целиком, а `pg`/`node-pg-migrate` — из
`optionalDependencies` в `package.json`.

### Включение

```bash
# .env
DATABASE_URL=postgresql://bot:bot@db:5432/bot
```

### Работа с миграциями

```bash
make up-local-db                          # поднять Postgres в Docker
make migration m="добавил таблицу users"  # создать ревизию (node-pg-migrate)
make migrate                              # применить
```

Миграции — обычные JS-файлы (`.node-pg-migraterc` задаёт `migration-file-
language: js`), DSN берётся из `DATABASE_URL` в `.env` — `make migrate` сам
подгружает `.env` перед вызовом `node-pg-migrate`.

### Использование

```typescript
import { UserRepository } from "./db/repositories/users.js";
import { getPool, withTransaction } from "./db/pool.js";

await withTransaction(async (client) => {
  await new UserRepository(client).upsert(123, "ivan");
});
```

Весь SQL держится в репозиториях. Обработчики к пулу напрямую не ходят: иначе
запросы расползаются по слоям и их невозможно ни переиспользовать, ни
протестировать отдельно.

## Docker

Образ многостадийный (`docker/Dockerfile`):

- **base** — зависимости и код, `pnpm build` в TypeScript; отдельный слой на
  `package.json`/`pnpm-lock.yaml`, чтобы правка кода не тянула переустановку
  пакетов;
- **test** — гоняет `biome check` и `vitest` внутри собранного образа; эту
  цель использует CI, проверяя ровно ту среду, что поедет на прод;
- **runtime** — прод-образ: `pnpm prune --prod` убирает dev-зависимости
  (typescript, vitest, biome, tsx), запуск от непривилегированного
  пользователя (`appuser`, uid 10001).

### Compose

`docker-compose.local.yml` собирает образ из исходников — разработчику нужно
видеть свои правки. Postgres вынесен в профиль `db` и без него не поднимается.

`docker-compose.prod.yml` тянет готовый образ из Harbor по тегу, выставляет
лимиты памяти и CPU и публикует бота через внешнюю сеть `maxbots-network`,
а не пробросом порта на хост.

Оба файла принимают `--env-file .env` — это обязательно. Без флага Compose
ищет `.env` рядом с самим compose-файлом, то есть в `docker/`, и подстановка
`${PORT}` в `ports:` молча берёт значение по умолчанию. Makefile подставляет
флаг сам.

Healthcheck в прод-конфигурации бьёт в `/healthz` (через `node -e`, без
дополнительных зависимостей) и потому работает только при `BOT_MODE=webhook`.
Для polling его нужно убрать, иначе исправный бот будет помечен `unhealthy`.

## CI/CD

### GitHub Actions (`.github/workflows/ci.yml`)

Три задачи: `lint` → `test` → `build`. Сборка проверяет валидность обоих
compose-файлов, собирает образ и публикует его в GHCR (на pull request —
только собирает, без публикации). Теги: `latest` на дефолтной ветке,
семантические на `v*.*.*`, `sha-<short>` всегда.

### Gitea Actions (`.gitea/workflows/pipeline.yml`)

Один файл на весь цикл: `lint` → `test` → `build` → `release-image` →
`deploy` → `rollback`.

**Почему один файл, а не ci.yml + cd.yml.** В Gitea Actions нет события
`workflow_run` ([gitea#24898](https://github.com/go-gitea/gitea/issues/24898)),
поэтому запустить деплой «после успешного CI» из отдельного файла нечем.
Единственный рабочий способ выстроить зависимость — `needs:` внутри одного
файла.

Не добавляйте рядом второй workflow с теми же триггерами: Gitea запускает
каждый файл в `.gitea/workflows/` независимо, и вы получите двойные прогоны.

**Что происходит при пуше тега `vX.Y.Z`:**

1. `build` собирает образ и публикует его как `sha-<short>`;
2. `release-image` находит этот образ и перетегивает в `vX.Y.Z` без
   пересборки (если не нашёл — собирает из исходников тега);
3. `deploy` копирует compose на прод-хост, сохраняет предыдущий тег в
   `.image_tag.previous`, делает `pull` и `up -d`, затем проверяет, что
   контейнер запущен и не уходит в рестарт-петлю;
4. `rollback` срабатывает автоматически при провале и возвращает предыдущий
   тег.

Файл `.env` через пайплайн не ходит: боевые секреты лежат на прод-хосте
постоянно.

**Требуемые Gitea Variables:** `HARBOR_REGISTRY`, `HARBOR_PROJECT`,
`HARBOR_IMAGE`, `RUNNER_LABEL`, `PROD_HOST`, `PROD_USER`, `PROD_PATH`,
`NPM_REGISTRY` (опц.).

**Требуемые Gitea Secrets:** `HARBOR_USERNAME`, `HARBOR_PASSWORD`,
`SSH_PRIVATE_KEY`, `NPM_REGISTRY_TOKEN` (опц.).

### Про smoke-тест образа

Полный старт бота в CI не проверяется: с плейсхолдер-токеном первый же запрос
к API вернёт ошибку авторизации, и гейт был бы красным при полностью исправной
сборке. Вместо этого проверяется импорт собранного модуля конфигурации внутри
готового образа — он тянет все зависимости и строит конфигурацию, то есть
ловит именно ошибки сборки, без сети и без реального токена.

## Закрытый контур

Шаблон настроен на работу за периметром, но остаётся работоспособным снаружи.

**По умолчанию** источники указывают на внутренние зеркала: `harbor.volganet.ru`
(образы), `nexus.volganet.ru` (APT), Gitea Variable `NPM_REGISTRY` (npm-прокси,
если он есть). Все они параметризованы.

**Сборка с доступом в интернет:**

```bash
BASE_IMAGE=node:22-bookworm-slim \
POSTGRES_IMAGE=postgres:16-alpine \
USE_NEXUS_APT=0 \
make up-local
```

Workflow для GitHub уже собирает с публичными источниками — у его раннера
доступа к контуру нет.

**Раннер Gitea.** В отличие от Python-версии шаблона (которой приходится
вендорить бинарь `uv` в `build/uv/`, потому что раннер не может скачать его с
astral.sh), здесь ничего вендорить не нужно: `corepack` (менеджер пакетных
менеджеров) входит в поставку Node.js, и `pnpm` активируется одной командой
`corepack enable`. Раннеру достаточно иметь предустановленный Node 22.

**Сертификаты.** Если цепочка API подписана УЦ, которого нет в системном
хранилище (например, Минцифры РФ), есть два пути — положить `.crt` в
`certs/` (действует на весь контейнер) или указать `MAX_CA_BUNDLE`
(действует только на соединения бота). Подробности в
[`certs/README.md`](certs/README.md).

**Токены в реестре.** `NPM_REGISTRY` может содержать креды внутреннего
npm-прокси. В пайплайне он маскируется и передаётся через окружение шага.

## Тесты

```bash
make test
```

36 тестов: разбор и валидация конфигурации, payload'ы кнопок, ограничитель
частоты, throttling-middleware, очередь фоновой обработки вебхука, нарезка
длинных сообщений.

Тесты герметичны: в сеть не ходят, реальный токен не используют, локальный
`.env` игнорируют (`src/config.ts` не грузит `.env`, когда переменная
`VITEST` выставлена — vitest сам её ставит на время прогона).

Помощник `withEnv()` из `tests/helpers/env.ts` задаёт переменные окружения так
же, как это делает прод, — заодно проверяется и сам разбор конфигурации:

```typescript
it("разбирает список admin id", () => {
  const settings = withEnv({ ADMIN_IDS: " 123, 456 ,789 " });
  expect(settings.adminIdsSet).toEqual(new Set([123, 456, 789]));
});
```

## Отличия от Python-версии

Короткий список мест, где TypeScript-порт устроен иначе, чем оригинал, и
почему.

**Свой HTTP-клиент вместо `maxapi`.** Официального Node/TS SDK для MAX не
существует. `src/max/` — тонкий клиент на undici, повторяющий поверхность API
использованных методов (`sendMessage`, `subscribeWebhook`, `getUpdates` и
т.д.). Пути эндпоинтов — лучшее приближение к официальному API; при
расхождении с документацией правки локализованы в `src/max/bot.ts`.

**Лимиты и ретраи — композиция, а не monkey-patch.** Python-версия патчит
методы внешней библиотеки `maxapi`. Здесь клиент собственный, поэтому
`runtime.ts::withRateLimitAndRetry` — обычная функция-обёртка, вызываемая
из `Bot.call()`.

**Webhook-сервер — `node:http`, без фреймворка.** Вместо FastAPI + uvicorn
здесь используется встроенный HTTP-сервер Node: обработчиков всего два
(POST-маршрут вебхука и `/healthz`), фреймворк не оправдан.

**`drain()` не отменяет задачи.** `asyncio.Task` в Python можно отменить;
`Promise` в JS — нет. По истечении `WEBHOOK_DRAIN_TIMEOUT` бот просто
перестаёт ждать, фоновые обработчики доработают самостоятельно (см. комментарий
в `src/webhook.ts`).

**Опциональные зависимости — `optionalDependencies`, а не `extras`.** В Python
`db`/`metrics` ставятся по требованию (`uv sync --extra db`, по умолчанию
отсутствуют). В Node аналог — `optionalDependencies` в `package.json`:
устанавливаются по умолчанию вместе с `pnpm install`, но код всегда
импортирует их лениво (`await import("pg")`), поэтому их можно убрать из
`package.json` полностью, если БД и метрики не нужны.

**DSN без суффикса драйвера.** Python-версия требует `postgresql+asyncpg://`
и проверяет это при старте — синхронный драйвер иначе не заработал бы molча.
`pg` в Node всегда асинхронный, поэтому `DATABASE_URL` — обычный
`postgresql://` без дополнительной проверки.
